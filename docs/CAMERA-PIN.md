# Stage 1 preparation — static camera / aim pins (read-only)

Status: **STATIC_SHAPE_ONLY** — not a hook, not a runtime confirmation, no game code executed.
Producer: `Recon assembly` (new read-only CLI/PE shape reader, `src/diagnostics/AssemblyEvidence.cs`), re-derived by the
verifier on every run (`assembly-pinning-recon`, `assembly-camera-pin` in `tests/verify.ps1`).
Source: `tools/interop/Assembly-CSharp.dll` (Cpp2IL/Il2CppInterop dummy assembly of the game's own code; git-ignored, not
redistributable) — size/sha256 are recorded in `docs/playtests/reports/static-stage0/pins/assembly-recon.json` under `source`.
Reports: `docs/playtests/reports/static-stage0/pins/assembly-recon.json` (type/member shape) and `artifacts/assembly-camera-pin/assembly-recon.json`
(member-level pin, regenerated by the verifier).

## Why this file exists

D-031/D-032/D-033/D-039 narrowed the gameplay camera's *runtime* neighbourhood to the player root
(`Prefab_Player_Level1`), which carries `PlayerController`, `BobAnimation` ×2, `ShakeAnimation`, `Tutorial`,
`UnityEngine.InputSystem.PlayerInput` and `PlayerInputController`, while the camera GameObject itself carries only
`UniversalAdditionalCameraData`. Which code **writes** the camera cannot be read off the executing game, and the
identifier-string scan (`static-recon.json`) cannot show *ownership* of a name. The dummy assembly can: it carries the
type → field/method shape of the game's code.

## What this evidence can and cannot show

- **Can**: exact type names, base types, interface lists, field/method names with bounded signatures, nesting, and
  whether a member has a method body at all (`HasBody`; 19,209 methods have stub bodies in this file).
- **Cannot**: what any method does. Interop/dummy method bodies are generated stubs, so no call site, assignment or
  transform write is visible here. Every conclusion below is a **ranked hypothesis to be confirmed at runtime**, never a
  hook. ("Never write *hook confirmed* until the game visibly responds.")

### Pinned conclusions (each with its confirmation step)

1. **Gameplay camera writer = `PlayerController`**, most plausibly its **`LateUpdate()`**: it is the only loop method on a
   component that holds the camera transform, and applying look *after* the animators explains the measured
   Update→LateUpdate rewrite (68% of frames moved, 4% rotated; D-039).
   *Confirmation (read-only, Stage 1 spike):* per-frame logging of `camera_transform` deltas against `current_mouse_look`
   / `target_fov`, plus — only if that is ambiguous — a logging-only Harmony **postfix** on `LateUpdate`.
2. **Bob/shake are inputs, not writers**: `BobAnimation`/`ShakeAnimation` only produce `displacement` /
   `angular_displacement`; the applier lives inside `PlayerController`, whose `head_bob`/`weapon_bob`/`shake_animation`
   fields are those instances. No separate applier type exists in the assembly.
3. **Aim/muzzle (LIM-003) narrowed**: the runtime `*Arm` leaves (`ArsenyArm`, `EngenierArm`, `ExagoraArm`, `LeslieArm`,
   `ReaperArm`, `SOSUKEArm`, `RomanCandleGatling_Anim`) are **per-hunter arm / weapon-animation variants** — no aim pivot
   appears among `get_*arm*` members, and `mechanical_arm_animator : Animator` sits on pet/companion scripts (`Snake`,
   `Fish`, `Frog`, `Orb`, `Rat`, `Werewolf`). A shot's aim source is on the weapon scripts (`Weapon.muzzle_position`,
   `Weapon.muzzle_flash_spawn`, `Weapon.shoot_forward(..., Transform)`).
   *Not closed:* which arm is live/active still needs one runtime observation (depth-4 dump or an active-state flag).
4. **FOV ownership**: `PlayerController` owns `target_fov`, `start_fov`, `play_fov_animation`/`stop_fov_animation` and the
   dash/overcharge FOV constants, so a VR camera takeover must stop fighting this pipeline, not only the look input.

## Honesty / limitations

- A name, signature or body presence is **not** a hook, call site or proof of who writes a transform.
- Type references are rendered by name from metadata; assemblies are never resolved, loaded or executed.
- Caps: 200,000 type definitions scanned, 1,200 matched types, 256 reported members per type, signature depth 12,
  1 s regex timeout. Truncation and unresolved-signature counts are explicit in the report (`unresolvedSignatureCount=0`
  for this file). `FieldCount`/`MethodCount` are metadata totals and are unaffected by a member filter.
- `SimpleCameraFP` is deliberately **not** claimed: the runtime component list and the cross-reference sweep both
  disagree with that plausible-looking name.
- Read-only: no game launch, no loader install, no native code loading, no game/save writes, no XR init.
